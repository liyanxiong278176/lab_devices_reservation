# ADR-0001：采用一次性 FastAPI 重写

- 状态：已接受
- 日期：2026-08-26
- 决策人：项目负责人

## 背景

现有项目后端是 Spring Boot，AI 能力基于 Spring AI，用户要求迁移到 Python FastAPI 与 LangChain，并同时解决并发、高可用、性能、安全和 AI 产品化问题。用户明确选择一次性重写，不采用长期双栈运行。

## 决策

构建新的 FastAPI 后端作为唯一运行面，完整迁移以下能力：认证授权、预约状态机、并发防超约、通知与超时任务、WebSocket、推荐、审计，以及 AI 会话、Agent Harness 和 Agentic RAG。Spring Boot 代码作为迁移参考和回滚前的历史实现，不作为新系统的线上依赖。

迁移必须配套：

1. 先定义领域级接口契约和数据迁移/回滚策略，再替换前端调用。
2. 使用可回滚的容器镜像、数据库向后兼容迁移、备份与演练，降低一次性切换风险。
3. 在切流前完成单元、契约、集成、并发、故障注入和 AI 行为评测；不以“服务能启动”作为迁移完成标准。
4. 新系统内部采用异步 I/O、明确的事务边界、幂等键、数据库条件更新/锁、任务领取和可观测性来满足高并发与高可用目标。

## 影响

### 正面影响

- 避免长期维护两套后端和两套领域逻辑。
- 可以从一开始统一 FastAPI 的异步模型、任务系统、认证、错误结构和 AI 运行时。
- 前端、后端和 AI 契约能够一起重构，减少兼容层对产品体验的限制。

### 代价与风险

- 上线切换风险高于分阶段迁移，必须有完整回滚和演练方案。
- 迁移期间需要同时完成领域逻辑重写、数据兼容、性能验证和前端适配。
- 旧 Spring 实现中的缺陷不能直接照搬，必须以领域不变量和测试作为迁移依据。

## 未决问题

本 ADR 不预先决定 Python 小版本、部署编排、接口版本策略、数据库是否继续使用 MySQL、以及停机窗口；这些决策在后续领域和部署确认中单独记录。
