# ADR-0003：采用单体 FastAPI 与内部异步运行时

- 状态：已接受
- 日期：2026-08-26
- 决策人：项目负责人

## 背景

项目希望具备高并发、高可用和 AI 能力，但当前阶段不希望维护 API、Worker、AI 服务三个独立部署单元。预约业务和 AI 仍然需要不同的并发、超时和资源控制策略。

## 决策

新系统采用模块化单体 FastAPI：认证、设备、预约、审批、通知、任务、Agent Harness 和 Agentic RAG 位于同一代码仓库和部署单元中。HTTP/WebSocket 请求使用异步 I/O；通知、超时取消、文档解析/索引、AI 执行等耗时工作进入内部异步任务运行时，并使用有界并发、超时、重试、幂等和优先级隔离。

单体不等于所有工作都在请求协程中直接执行：

- 预约写操作在请求内完成必要的事务和一致性检查，不能因为异步化而返回未落库的“成功”。
- AI 模型调用和工具循环不能阻塞事件循环，必须交给受控的异步执行器/任务消费者，并限制每用户、每租户和全局并发。
- 异步任务不能只依赖进程内内存队列或 FastAPI `BackgroundTasks`；任务必须先有持久化记录，再由内部消费者处理。
- 所有任务都要能在进程重启后恢复，且重复执行不会重复发送通知、重复写预约或重复执行写工具。

## 影响

### 正面影响

- 部署、调试、权限和领域代码的复杂度低于微服务拆分。
- 仍可以通过异步 I/O、连接池、批量处理、限流和任务并发控制提高吞吐。
- 后续若 AI 或索引负载明显增长，可以在保持领域接口不变的前提下再拆分。

### 限制与风险

- AI 高峰和预约高峰共享部署单元，必须实现资源隔离，否则 AI 会挤占事件循环、线程池、连接池或内存。
- 单体副本扩展时，任务领取、定时任务和 WebSocket 状态不能依赖本地内存。
- 单体部署在单台主机上不能真正提供高可用；至少需要可重启的副本、反向代理/负载均衡、外部化数据和恢复演练。

## 未决问题

可靠异步任务的具体投递、重试、死信、消费组和与 MySQL 事务的一致性策略，需要单独确定。
