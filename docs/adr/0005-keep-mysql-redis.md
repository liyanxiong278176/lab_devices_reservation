# ADR-0005：本次重构保留 MySQL 8 与 Redis 7

- 状态：已接受
- 日期：2026-08-26
- 决策人：项目负责人

## 背景

现有系统的核心数据已经位于 MySQL，Redis 承担分布式锁、缓存和实时通信辅助能力。此次目标是更换应用框架、重构领域能力和建设完整 AI 系统，同时还要提升并发、高可用和性能。

## 决策

本次不迁移事务数据库：

- MySQL 8 继续作为用户、角色、设备、预约、审批、通知、审计和任务记录的事实来源。
- Redis 7 继续用于缓存、分布式锁、限流、实时事件分发或任务加速，但不作为不可恢复业务数据的唯一来源。
- 预约场景采用 Redis 锁故障可降级策略：Redis 正常时用于减少并发竞争，Redis 不可用或获取锁超时时仍继续执行 MySQL 事务，由预约日期唯一约束作为最终防超约依据；因此 Redis 故障可能增加数据库竞争，但不会直接让预约功能整体不可用。
- 通过新的数据库迁移脚本补齐任务表、Outbox、幂等键、版本字段、索引和 AI/RAG 元数据；不直接修改已发布的历史迁移脚本。
- 向量存储是否单独引入，在 Agentic RAG 设计阶段独立决策，不改变预约事务模型。

## 影响

### 正面影响

- 避免应用重写和数据库迁移叠加，降低一次性切换风险。
- 可以复用已有数据、备份、监控和运维经验。
- MySQL 事务可以直接承载预约一致性、Outbox 和任务恢复。

### 限制与风险

- 新的 Python 数据访问层必须严格验证旧表的实际约束、字符集、时区、索引和历史脏数据。
- Redis 故障时，锁、缓存和实时推送需要明确降级；不能因为 Redis 不可用而破坏预约唯一性。
- RAG 的向量检索能力不能假设 MySQL 当前表结构天然具备，需要另行评估持久化向量存储。
