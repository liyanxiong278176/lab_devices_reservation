# ADR-0004：异步任务必须持久化并可恢复

- 状态：已接受
- 日期：2026-08-26
- 决策人：项目负责人

## 背景

系统包含通知、预约超时取消、文档解析/索引和 Agent 相关异步工作。单纯使用 FastAPI 进程内的 `BackgroundTasks` 或 `asyncio.Queue`，在进程崩溃、发布重启或多副本部署时会丢任务，也无法可靠处理重复消费。

## 决策

所有重要异步任务都必须具备持久化任务记录，并满足：

- 业务事务成功与任务记录之间具有可恢复的一致性，不能出现业务已提交但任务完全无从追踪的状态。
- 服务重启后可以扫描并继续未完成任务。
- 临时失败按退避策略重试，超过阈值进入可观测的死信/失败状态。
- 任务携带幂等键，重复消费不能重复发送通知、重复执行预约写操作或重复生成索引结果。
- 任务处理使用有界并发、超时、取消和优先级，AI 任务不能无限占用预约业务的资源。

本次实现采用 MySQL Outbox/任务表作为可靠事实来源。Redis 只承担缓存、分布式锁、限流和可选的任务加速，不承担不可恢复任务的唯一持久化责任，也不引入 Kafka、RabbitMQ 等额外消息服务。任务领取采用数据库事务和租约式状态转换，重复执行通过幂等键和业务状态机消除。

## 影响

- 服务重启和短暂 Redis/网络故障不会直接导致任务永久丢失。
- 数据库会增加任务记录、索引、清理和监控成本。
- “发送一次”不能依赖技术幻觉；外部通知需要幂等键或业务侧去重，任务执行需要状态机/CAS。
