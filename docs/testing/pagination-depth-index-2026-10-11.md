# 1 万条预约单并发：统计信息、覆盖索引、页深与 SQL/HTTP 对比

本次按要求保持 10,000 条预约、单并发，刷新统计信息后分别测浅页、中页和深页。结论：1 万条数据已足以观察延迟关联的深页主查询收益；正确的覆盖索引能显著减少该查询的记录读取与排序成本。完整接口收益受其他阶段和运行波动影响，不能承诺所有页都更快。

所有实验 DDL 仅在本次创建的 `lab_resume_d4afe495` 隔离库执行。生产模型、生产索引、现有迁移与 `.env` 均未改动；候选索引尚未作为 Alembic revision 落地。实验结束后临时数据库、临时 Redis 和本次启动的 API 进程已清理。

## 条件与公平性

- 真实 MySQL 8.0.46、Redis 7、FastAPI，现有迁移 head 为 `0038_penalties_overdue`。
- 同一个隔离库、100 台设备、10,000 条单学院单用户的已完成预约；每页 20 条。
- 固定第 1、250、500 页，OFFSET 分别为 0、4,980、9,980。
- 两种索引状态：当前生产索引；在其基础上增加实验索引 `idx_resume_user_college_id(user_id, college_id, id)`。
- 每种索引状态都比较传统完整行 `OFFSET/LIMIT` 与原生产延迟关联方法；权限、学院过滤、排序、COUNT、关联加载、认证和返回字段相同。传统基线仅在独立基准进程替换应用服务方法。
- 四轮交替索引状态顺序和分页方案顺序，并轮换页深顺序。每个计时块顺序预热 50 次；两种方案始终串行执行，不进行并发请求。
- 每个索引/页深/分页方案分层：SQL 每轮 500 次，共 2,000 条样本；HTTP 每轮 250 次，共 1,000 条样本。总计正式 SQL 24,000 次、HTTP 12,000 次。
- 每次索引阶段开始前执行 `ANALYZE TABLE reservation`，检查返回 `OK`；八个阶段均成功。没有 `FORCE INDEX`。
- 每个分层的汇总 P95 从该分层全部原始样本计算最近秩分位数；不平均各轮 P95，不把不同页深或索引状态混算。

SQL 指分页主 SELECT 的客户端执行、驱动往返、缓冲结果解码和读取，不是仅由 MySQL 内部统计的执行时间；排除取连接、认证、COUNT、ORM 关联加载和接口响应序列化。HTTP 指完整鉴权接口的响应体接收，包含这些公共业务阶段，排除登录、预热、JSON 校验及响应摘要计算。两层 P95 不能直接相减，推算其他阶段的 P95。

## 统计信息与覆盖路径验证

首次造数后，主键索引基数估计为 1；主动刷新后为 10,057。基数是估计值，实际预约数量通过 `COUNT(*)` 核验为 10,000，目标用户及学院范围内也为 10,000。

当前索引下，第 500 页 ID 子查询实际计划使用学院索引与用户索引的交集，再检查条件、排序后分页。候选索引下，优化器自动选择 `(user_id, college_id, id)`；ID 子查询及完整延迟关联语句内的该路径均显示 `using_index=true`。四轮、三种页深全部验证成功。

第 500 页的一次实际计划示例：

```text
Limit/Offset: 20/9980
  Covering index lookup using idx_resume_user_college_id
    (user_id=2, college_id=5), reverse, rows=10000
Single-row lookup using PRIMARY: rows=1, loops=20
```

这条路径仍需扫描约 10,000 条索引项，但仅对本页 20 条记录按主键加载完整行；没有通过延迟关联消除 OFFSET 的扫描成本。外层只排序本页 20 条记录。

## 全部分层汇总

以下均为 P95，单位 ms。每一行中的传统/延迟方案使用同一种索引状态。

| 索引状态 | 页码 | SQL：传统 | SQL：延迟关联 | HTTP：传统 | HTTP：延迟关联 |
|---|---:|---:|---:|---:|---:|
| 当前索引，统计已刷新 | 1 | 3.179 | 3.646 | 59.158 | 51.183 |
| 当前索引，统计已刷新 | 250 | 13.623 | 13.479 | 54.347 | 62.255 |
| 当前索引，统计已刷新 | 500 | 19.282 | 15.529 | 65.415 | 64.539 |
| 增加覆盖索引，统计已刷新 | 1 | 3.031 | 2.752 | 39.074 | 41.893 |
| 增加覆盖索引，统计已刷新 | 250 | 8.005 | 3.938 | 70.617 | 42.680 |
| 增加覆盖索引，统计已刷新 | 500 | **17.146** | **7.016** | **69.021** | **45.442** |

在双方使用相同覆盖索引的第 500 页测试中，延迟关联 SQL P95 低 10.130 ms（59.08%），完整接口 P95 低 23.579 ms（34.16%）。这是本次同条件测试的汇总观测值，不代表固定性能比例或生产 SLA。

浅页没有一致的接口改善；例如覆盖索引下，第 1 页延迟关联 HTTP P95 反而高约 2.82 ms。当前索引下，第 250 页接口也更慢。因此不宜把深页结果表述为所有页面统一加速。

## 深页四轮复测及波动

以下均为双方使用同一个覆盖索引、第 500 页的 P95，单位 ms。

| 轮次 | SQL：传统 | SQL：延迟关联 | HTTP：传统 | HTTP：延迟关联 |
|---|---:|---:|---:|---:|
| 1 | 13.243 | 4.031 | 40.038 | 40.312 |
| 2 | 12.763 | 4.581 | 46.062 | 40.452 |
| 3 | 14.304 | 4.766 | 51.093 | 38.748 |
| 4 | 24.112 | 11.111 | 108.298 | 56.859 |

SQL 四轮均更低，说明覆盖索引配合延迟关联在此深页查询上有重复出现的收益。HTTP 三轮更低，首轮基本持平；第四轮多个分层出现明显尾延迟波动，尤其传统方案，拉大了汇总差异。所有样本均保留，未剔除该轮。没有逐阶段资源采样，不能把波动确定归因为某个后台进程、CPU 或磁盘事件，也不能把 34.16% 描述为稳定的长期收益。

本次实验验证了索引路径与页深对收益的重要性，没有加入未刷新统计信息的同期控制组，因此不能精确量化刷新统计信息本身的独立收益。此前全页混合基准与这次固定页深、增加覆盖索引的实验属于不同条件，不能拼接其中的 A/B 数字。

## 可用于说明实验结果的表述

> 在 1 万条预约、单并发、第 500 页（每页 20 条）的隔离测试中，验证用户/学院/ID 覆盖索引与延迟关联分页；相比使用相同索引的传统分页，SQL 主查询 P95 从 17.15 ms 降至 7.02 ms，完整接口 P95 从 69.02 ms 降至 45.44 ms。

该表述必须保留测试场景和深页范围。候选索引目前仅在实验库验证，不应表述为已经部署到生产；若将索引正式落地，应新增 Alembic revision，并验证升级、现有列表查询与写入兼容性。
