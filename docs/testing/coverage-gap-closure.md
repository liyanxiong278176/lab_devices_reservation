范围：FastAPI、MySQL、Redis、Vue、浏览器和运行恢复链路；AI 功能不在本轮验证范围内。

## 风险与验证追踪

| 风险 | 影响 | 验收条件 | 验证类型 | 状态 |
|---|---|---|---|---|
| 同设备同日期被重复预约 | 业务数据超约 | 并发竞争只保留一个占用；部分区间重叠也不能双重占用；冲突反馈无 5xx | MySQL/Redis 并发集成、HTTP 黑盒 | MySQL/Redis 集成与历史 HTTP 竞抢已覆盖；本轮新手工链路覆盖多用户预约和冲突预检，但没有声称完成同设备同时双提交 |
| 锁过期、旧持有者误删新锁 | 临界区重叠、数据损坏 | 超长任务租约续期；旧持有者释放不得移除新锁；Redis 异常仍由 MySQL 约束兜底 | Redis 故障/时序集成 | 已有覆盖；最后做实际浏览器业务验证 |
| 跨学院越权或撤权未生效 | 数据泄露、越权审批 | 直接接口和页面同时验证；权限变化后旧会话不能继续访问 | 安全负向测试 | 基础覆盖；补充 OWASP 风险清单验证 |
| 通知丢失或重复消费 | 用户错过审批结果、重复副作用 | 断线补查可恢复；Worker 重启后任务可回收；重放不产生重复通知或状态变更 | Outbox/HTTP/WebSocket 故障测试 | 已有覆盖；补充进程重启场景 |
| 负载升高导致错误或资源耗尽 | 服务不可用、长尾延迟 | 记录目标负载、p95/p99、错误率及资源；超载可控拒绝，恢复后请求成功 | 常态、升压、突发、极限、长稳 | 已完成本机曲线；非生产容量认证 |
| 页面只在单一桌面浏览器可用 | 用户无法完成业务 | 生产构建在 CI 冒烟；主流程覆盖多视口、键盘操作和关键可访问性规则 | 浏览器系统/无障碍 | 学生和管理员本轮新会话全链路通过；Chromium 以外的浏览器仍未覆盖 |
| 数据库/缓存/Worker 故障后不能恢复 | 业务卡住、通知漏发 | 注入依赖中断与进程重启；恢复后数据不丢、不重放副作用；备份可恢复并通过一致性校验 | 故障注入/恢复演练 | MySQL/Redis 故障恢复及 Outbox 租约回收已通过；备份恢复未在本轮执行 |

## 覆盖率基线

代码覆盖率是定位遗漏分支的辅助信号，不代替需求覆盖或断言质量。本项目用 `.coveragerc` 排除 AI 模块，只统计非 AI 后端代码；前端覆盖率排除 AI 页面和用例，并单独报告，不与后端百分比混算。后端以当前实测组合覆盖率为基线设 66% CI 下限；前端仅对已有稳定单元测试的请求安全层、WebSocket 通知和分页工具设逐文件门槛，未把未做 coverage instrumentation 的 E2E 页面硬算成 0 分。

### 阶段 1：风险追踪与覆盖率

- 风险追踪矩阵已建立，覆盖预约唯一性/锁租约、学院授权、通知恢复、容量、前端可用性和依赖恢复，并要求每项关联明确验收条件。
- 第一次覆盖率试跑因 `-k 'not ai'` 错误匹配 maintenance 一词而误删 60 个用例，整次结果作废；随后改为忽略 AI 测试文件并仅显式排除上传配额文件中的单个 AI 用例。
- 本轮 CI 配置等价的非 AI 后端完整测试（独立 MySQL/Redis，开启可选集成及 1000 并发场景）：137 passed、1 skipped、1 个 AI 用例 deselected；组合覆盖 67.76%，高于 66% CI 下限。另单独开启 `LAB_TEST_REDIS_URL` 后，通知中继的 3 项测试全部通过。限流回退用例首次受 CI 的 `LAB_RATE_LIMIT_ENABLED=false` 覆盖而未触发限流；为这 3 项测试显式启用被测功能后，在相同 CI 环境下通过。
- 前端非 AI Vitest 覆盖命令：13 个文件、71 项通过；全源代码行覆盖 14.60%、分支覆盖 9.97%。本轮通知去重增加缓存上限分支后，首次 coverage gate 因该分支未覆盖而失败；补充 513 个不同通知 ID 后重放最早 ID 的边界验证，逐文件行/分支门槛通过。全量 `pnpm test` 为 14 个文件、76 项通过。
- 首次前端覆盖率执行失败，根因是仓库未安装 `@vitest/coverage-v8`；新增与 Vitest 4.1.9 对齐的 provider 后，覆盖命令及门槛通过。
- 阶段结论：测量和 CI 防回退已补齐；全源覆盖率仍显示有测试欠账，后续安全与多用户页面阶段针对高风险路径补新场景，不以机械提高百分比代替风险验证。

### 最新非 AI 覆盖率与 API 补测

- 后端全量回归：260 passed、19 skipped；Ruff 检查通过。非 AI 后端分支组合覆盖率为 83%。预约 API 新增场景使该路由覆盖率达到 100%；报修 API 路由覆盖率为 91%，报修应用服务为 85%。
- 前端：Vitest 45 个文件、199 项通过；构建通过。非 AI 覆盖报告：语句 39.89%、分支 28.14%、行 41.19%、函数 32.44%。这是全源总体欠账信号，不能用手工 E2E 替代尚未覆盖的组件分支。
- 真实依赖集成：MySQL 预约并发/区间重叠及 1,000 请求场景 6 passed；Redis 日期锁、重入、看门狗与旧持有者释放场景 6 passed；通知中继 3 passed；认证会话轮换与撤权 3 passed。
- 构建仍输出大 chunk 和 VueUse PURE 注释警告，但没有阻止构建；这些属于后续包体优化事项，不是本轮功能失败。

### 本轮新增的独立多会话页面复验（2026-09-28）

- 最后阶段才启动三名子智能体，使用两个普通用户和一个负责人账号、独立 Chromium 会话、自建 runner 与全新 `e2e-qa260928-multi9x3` 数据；没有运行或复用仓库中已有 Playwright 用例。
- A 创建预约 #51319（设备 #11629），B 创建预约 #51318（设备 #11628），页面提交均为 HTTP 201。管理员从详情抽屉核对预约身份后审批，两笔审批均为 HTTP 200。管理员在实际交接页面上传照片、核对配件并完成交接，两笔均为 HTTP 200、进入 `IN_USE`。
- A 保持在线：收到预约审批、交接、归还待验收和验收 WebSocket 消息，并在页面展示 toast；通知历史请求均为 HTTP 200。B 在审批及交接阶段断网，恢复后观察到旧 WebSocket 关闭、新 `/api/v2/ws` 建立；通知历史 HTTP 200 返回 6 条关联 #51318 的记录，包含审批和交接消息，证明使用 HTTP 历史补偿。该轮没有把 B 的实时帧作为通过证据。
- 两位用户分别通过真实页面上传归还照片并提交，管理员在待验收队列看到两条带照片记录并验收。独立只读 MySQL 查询核实 #51318/#51319 均为 `COMPLETED`、交接状态 `RETURNED`；管理员只读详情请求也都为 HTTP 200，待验收队列为 0。
- 首轮手工 runner 遇到管理员页面在预约创建前加载、列表用途文本被截断，以及把登录前 `/auth/me` 的预期 401 误报为 console error。分析后通过真实页面刷新、打开申请详情抽屉核验、区分匿名认证探测和非预期错误完成复测；没有为这些测试时序/断言问题修改业务代码。最终记录 0 个非预期 HTTP、浏览器或请求错误。
- 本轮双用户链路不是同一设备同时提交的竞抢：B 先占用 #11628 后，A 改用 #11629 才完成全生命周期。并发正确性依据 MySQL/Redis 集成和前述独立 HTTP 并发结果；不要将本轮人工流程描述成重新验证了同设备并发竞抢。

## 覆盖结论与尚未验证的边界

- 本轮已覆盖单元/分支、MySQL 与 Redis 集成、8 请求及 1000 请求并发、k6 常态/升压/突发/极限/长稳曲线、黑盒安全负向、生产预览 UI/无障碍与多用户完整浏览器链路。测试方法按风险、层级与故障类型组合，而不是仅以覆盖率判定质量；这与 ISTQB 的测试层级/类型及风险分析、OWASP WSTG 安全测试分类、Grafana k6 的负载 profile 建议一致。
- 不能据此断言系统没有问题。后端仍有低覆盖模块（例如设备权限 API、设备 API、报表 API、RBAC API）；前端全源行覆盖只有 14.60%，大部分页面逻辑未由 Vitest instrumentation 覆盖，虽然本轮对关键流程做了手工页面联调，但没有逐页穷尽全部功能、角色和异常组合。
- 本轮只在 Chromium 做真实浏览器验收；未做 Firefox/WebKit 全矩阵。备份恢复演练未执行。k6 与依赖故障实验都在本机隔离容器中完成，不能作为生产容量、SLA 或真实集群多实例容量认证。
- AI 功能按范围排除；只对共享通知/认证依赖做非 AI 回归，没有评估 AI 业务质量。
