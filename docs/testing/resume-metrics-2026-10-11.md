## 可采用的通知表述

> 基于 MySQL Outbox、Redis Streams 和 SSE 实现异步通知及断线补偿；真实浏览器测试中，断线期间新增的 100 条通知在重连后全部按序恢复，未出现丢失或重复展示。

断线前先接收 A/B 两条通知，游标为 `2`。代理关闭 SSE 并暂停重连；100 条新通知经 Outbox 全部落入 MySQL 后才恢复代理。实际重连带 `Last-Event-ID: 2`；CDP 捕获 100 条补发通知，序号连续为 `3–102`，100 个不同通知 ID，缺失 0 条、重复 0 条。`batch-complete` 表示 `deliveredCount=100`、`omittedCount=0`。前端显示一次批次同步提示，逐页核验通知中心全部 102 条记录，其中 100 条离线通知各显示一次。

这里“展示一次”指通知中心记录，不代表为补发通知逐条弹出 100 个 toast。测试覆盖恰好 100 条通知的单次 SSE 补发上限，不声称超过上限时仍仅靠 SSE 全量重放。

## 旧单并发全页顺序请求复测（未主动刷新统计信息）

按最新要求，重新生成同一隔离库中的 10,000 条预约，单并发请求完整 `/api/v2/reservations/mine` 接口：每次响应接收并校验完成后，才发送下一次请求。两种方案每轮各正式请求 1,000 次，覆盖 500 页、每页读取两次；六轮交替执行顺序，每轮每种方案另顺序预热 500 次，不计入统计。每种方案共 6,000 条正式样本，汇总 P95 直接从全部样本计算，不是六个 P95 的平均。

### 为什么延迟关联可能更慢

当前执行计划确认，两种方案都从 `idx_reservation_college_v2` 查询学院数据，再检查 `user_id`；第 500 页两者均扫描 10,000 条匹配记录。现有学院索引不能同时覆盖用户过滤，ID 子查询仍需读取记录以检查用户条件，未实现完全只读覆盖索引、仅对本页回表的理想路径。延迟关联还增加子查询物化、主键 JOIN 和外层排序（排序本页 20 条）步骤。

此次 P95 衡量完整 HTTP 响应，包含请求认证、总数计数、关联加载及响应序列化。分页主查询的收益只影响其中一部分，而且负载均匀覆盖浅页与深页。因此，仅凭采用延迟关联不能保证端到端 P95 降低。

这解释了当前查询结构的收益限制，**不等于已精确定位 2.33 ms 差异的全部原因**。该次第 500 页 `EXPLAIN ANALYZE` 中，传统主查询约 10.2 ms，延迟关联约 7.65 ms；这只是单次数据库语句执行，不能当作完整接口 P95，也无法证明端到端差异一定由 JOIN 造成。各轮存在时间波动，精确归因仍需逐阶段计时。单并发复测已经表明，先前上升不能仅归因于并发。

当前可用于简历的表述：

> 实现预约历史列表的延迟关联分页与稳定排序，在 1 万条预约、单并发顺序查询条件下完成六轮对比测试；500 页返回结果一致，12,000 次正式查询全部成功，延迟关联方案接口 P95 为 54.81 ms。

## 历史 20 并发对比方法（保留追溯）

在同一隔离数据库生成 100 台设备、10,000 条已完成预约，每页 20 条，共 500 页。传统方案在专用基准进程使用完整行 SQL `OFFSET/LIMIT`；延迟关联方案运行原生产方法，先对 ID 子查询分页，再 JOIN 加载本页完整记录。两者保留相同权限/学院过滤、筛选、ID 倒序、总数计数、五组 ORM 关联加载、认证、连接池和响应序列化，索引保持相同；没有把全部实体加载到 Python 后再切片。

六轮正式对比，每轮每种方案 1,000 次请求、20 并发，500 页各读取两次。先后顺序交替，两种方案各有三轮先执行。每轮每种方案先以相同并发预热全部 500 页；登录和预热不计入延迟。限流和业务后台 Worker 关闭。每页完整响应摘要及额外状态筛选一致，12,000 次正式查询全部 HTTP 200。
