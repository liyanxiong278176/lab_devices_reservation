# 10 万条预约：传统分页与延迟关联的单并发验证

本次在隔离 MySQL 库内生成并核验 **100,000 条预约**，单并发，对固定浅页、中页、深页执行四轮 SQL 与完整 HTTP 对比。现有生产索引下，第 5,000 页完整接口 P95 从 **214.122 ms 降至 165.325 ms（22.79%）**；双方使用同一个实验覆盖索引时，从 **172.975 ms 降至 67.332 ms（61.07%）**。两种索引状态的深页 SQL 与接口在四轮中均低于传统方案。

数据量增加并不保证所有页面加速：浅页没有改善，现有索引下第 2,500 页接口反而更慢。因此以上收益必须限定为对应索引、单并发、每页 20 条、第 5,000 页的场景。

## 测试数据与复现

生成器在专用测试学院、用户下创建 100 台设备、100,000 条已完成预约，按 1,000 条批次写入并一次提交。该夹具用于列表读取性能验证；预约主体有设备关联，不补齐履约、预约日占用、验收等关联明细。生产业务数据、模型、索引、迁移和 `.env` 未改动。

实际数据库 `COUNT(*)`、目标用户/学院范围计数、各次接口总数均校验为 100,000。首次主动刷新统计信息后，主键基数估计为 99,214；基数为估计值，不代表实际行数减少。每个索引阶段均执行 `ANALYZE TABLE reservation` 并检查成功。

## 对比方法

- 真实 MySQL 8.0.46、Redis 7、FastAPI；迁移 head 为 `0038_penalties_overdue`。
- 每页 20 条，固定第 1、2,500、5,000 页，OFFSET 分别为 0、49,980、99,980，符合最多跳过 100,000 条的限制。
- 比较当前生产索引，以及增加实验索引 `idx_resume_user_college_id(user_id, college_id, id)` 的状态。每种状态内，传统与延迟关联使用完全相同的索引。
- 传统基线为完整行 SQL `OFFSET/LIMIT`；延迟关联使用原生产方法，在 ID 子查询内完成相同权限/学院过滤、排序和分页，再加载本页完整记录。基线替换仅发生在专用测试进程。
- 两种方案保持相同用户、数据、筛选、排序、COUNT、五组 ORM 关联加载、认证、连接池及响应序列化；限流和后台 Worker 关闭。
- 四轮交替索引状态和方案执行顺序，轮换页深顺序。每个计时块顺序预热 50 次，预热与登录不计入统计；无并发请求。
- 每个索引/页深/方案分层每轮 SQL 250 次、HTTP 125 次，四轮分别累计 1,000/500 条样本。共 96 个计时块、正式 SQL 12,000 次、HTTP 6,000 次。
- 每个分层的 P95 使用全部原始样本的最近秩分位数，不平均各轮 P95，不混合不同页深或索引状态。

SQL 计时涵盖分页主 SELECT 的客户端执行、驱动往返和缓冲结果读取；排除连接池取连接、认证、COUNT、关联加载与接口序列化。HTTP 计时覆盖完整鉴权接口响应体接收，排除登录、预热、JSON 校验及摘要计算。SQL 指标不是仅由 MySQL 内部统计的执行时间，不能与 HTTP P95 相减推算其他阶段 P95。

## 分层汇总

以下均为 P95，单位 ms。每一行中的两种分页使用相同索引状态。

| 索引状态 | 页码 | SQL：传统 | SQL：延迟关联 | HTTP：传统 | HTTP：延迟关联 |
|---|---:|---:|---:|---:|---:|
| 现有索引 | 1 | 3.018 | 3.537 | 73.540 | 75.853 |
| 现有索引 | 2,500 | 81.012 | 81.433 | 165.828 | 362.068 |
| 现有索引 | 5,000 | **137.115** | **61.065** | **214.122** | **165.325** |
| 增加覆盖索引 | 1 | 3.460 | 3.797 | 51.253 | 55.585 |
| 增加覆盖索引 | 2,500 | 58.445 | 11.045 | 108.991 | 61.858 |
| 增加覆盖索引 | 5,000 | **123.365** | **18.555** | **172.975** | **67.332** |

第 5,000 页：

| 相同索引下的传统→延迟关联 | SQL P95 减少 | 完整接口 P95 减少 |
|---|---:|---:|
| 现有索引 | 76.050 ms，55.46% | 48.797 ms，22.79% |
| 增加覆盖索引 | 104.810 ms，84.96% | 105.643 ms，61.07% |

不能把现有索引传统方案的 214.122 ms 与覆盖索引延迟方案的 67.332 ms 拼成“延迟关联单独带来的提升”；那同时改变了索引。上表保持同索引 A/B。

## 执行计划与独立核验

没有 `FORCE INDEX`。四轮、三种页深的 ID 子查询和完整延迟关联语句内的分页路径均实际采用候选覆盖索引，JSON 计划显示 `using_index=true`；实际计划显示覆盖索引读取后，本页完整记录按主键查询 20 次。第 5,000 页仍扫描约 100,000 条索引项，延迟关联没有消除 OFFSET 扫描成本。

独立审计核验：

- 实际预约数量、生成记录和报告行数均为 100,000。
- 24 个汇总分层的 P50/P95/P99、96 个计时块的 P95 从原始样本重算一致。
- 正式 HTTP 6,000 次均为 200，SQL 12,000 次均返回 20 条；同层同页在所有轮次、方案、索引状态下的完整结果摘要一致。
- 18,000 条正式计时样本区间重叠为 0，符合单并发。
- 八个阶段 `ANALYZE TABLE` 成功，12 个覆盖分层的 ID/完整延迟语句路径和 20 次主键查找均验证。
- 本次创建的测试进程、Redis 容器、数据库已清理。

初始 `database-evidence.json` 的行数字段因局部变量遮蔽而记录错误，已恢复为经过生成日志及实际 `COUNT(*)` 验证的 100,000，并保留修正前原件。该问题仅涉及元数据，SQL、执行计划和计时样本未变；生成器、接口总数、实际数据库数量与最终报告均独立核验。

## 简历表述

现有索引方案对应当前业务实现，可使用：

> 采用延迟关联优化预约历史深页查询，在 10 万条预约、单并发、第 5,000 页（每页 20 条）测试中，相比传统分页，完整接口 P95 从 214.12 ms 降至 165.33 ms，降低 22.79%。

若描述覆盖索引实验，应明确实验范围：

> 在隔离环境验证用户/学院/ID 覆盖索引配合延迟关联分页；10 万条预约、单并发、第 5,000 页场景下，相比使用同一索引的传统分页，接口 P95 从 172.98 ms 降至 67.33 ms，降低 61.07%。

候选覆盖索引仅在测试库中创建，尚未新增生产 Alembic revision，不应表述为已部署生产。原 1 万条实验和本次 10 万条实验的页深、样本数及运行时间不同，不拼接其数值作为同条件 A/B。
