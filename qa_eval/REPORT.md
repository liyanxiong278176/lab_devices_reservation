## 并发与一致性

| 场景 | 预期 | 实测结果 | 判定 |
|---|---|---|---|
| 同设备同日，50 个独立请求 | 1 个成功，其余 409；数据库仅占用一天 | 1×201、49×409；新连接读取占用数为 1 | 通过 |
| 同设备同日，100 个独立请求 | 1 个成功，其余 409；数据库仅占用一天 | 1×201、99×409；新连接读取占用数为 1 | 通过 |
| 两个部分重叠日期区间竞争 | 重叠日期最多一个预约获得 | 1×201、1×409；无重复占用行 | 通过 |
| 首尾相邻日期 | 两个独立预约都可成功 | 2×201 | 通过 |
| 同日不同设备 | 两个独立预约都可成功 | 2×201 | 通过 |
| Redis 锁不可用时预约 | 数据库约束仍保证仅一个赢家 | 1×201、1×409；新连接读到 1 个占用日；锁降级指标增加 2 次 | 通过 |
| Redis 会话存储不可用 | 认证失败关闭 | HTTP 503 `AUTH_SESSION_UNAVAILABLE` | 通过 |

预约锁降级没有让业务正确性依赖 Redis；在 MySQL 中核对了新连接读到的占用行。并发

## 性能实测

### 负载 smoke 与尚未完成的容量档位

早期 Locust smoke 使用 10 个混合角色虚拟用户运行 20 秒，发送 117 个请求，无失败，约
5.87 RPS；汇总 P50/P90/P95/P99 分别为 23/130/390/450 ms。该次汇总包含登录请求，登录
自身 P95 为 450 ms；设备列表 P95 为 82 ms，预约创建 P95 为 160 ms，预约列表 P95 为
74 ms，通知历史 P95 为 36 ms。按计划中“汇总 P95 < 300 ms”的阈值，汇总值**未达标**；
主要接口样本低于该阈值。该记录发生在最新版 Locust 内存停止阈值加入前，只作为早期
基础 smoke，不代表当前版本的容量结论。

主机可用物理内存曾下降到约 1.53 GB（9.8%），因此停止进一步施压；结束检查时约有
1.94 GB 可用。25/50/100/200 用户档位、stairs、stress、spike 和 30 分钟 soak 均未执行。
这些结果属于**主机安全阈值限制**，不能当作应用容量测试通过，也不能推断最大并发用户数。

### 分页：1k / 10k / 100k 行，三次采样中位数

下表的 API 列是实际接口响应；SQL 两列在同一 MySQL 数据集上对比完整行 OFFSET 与 ID
分页后回表。深页提升率按 `(OFFSET - ID分页回表) / OFFSET` 计算。

| 数据量 | 页码 | 完整行 OFFSET SQL | ID 分页后回表 SQL | 实际 API | 深页 SQL 降幅 |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 1 / 50 | 4.39 / 3.22 ms | 2.16 / 2.44 ms | 33.80 / 26.55 ms | 24.3% |
| 10,000 | 1 / 500 | 2.69 / 10.92 ms | 2.88 / 3.78 ms | 34.60 / 34.70 ms | 65.4% |
| 100,000 | 1 / 5,000 | 4.25 / 100.10 ms | 4.03 / 15.89 ms | 76.86 / 110.50 ms | 84.1% |

1k 深页的绝对耗时很低，因此小幅差异可能来自测量噪声；在 100k 深页，回表分页 SQL
中位数从约 100.10 ms 降至 15.89 ms。接口耗时还包括鉴权、服务及序列化，不应与裸 SQL
耗时混为一谈。原始采样见 [pagination-6148dc58ed.json](results/pagination-6148dc58ed.json)。

### 缓存与 Redis 降级

| 模式 | 三次中位数 | 正确性/观测 |
|---|---:|---|
| API 缓存 miss | 31.20 ms | Redis miss 计数增长；MySQL 全局查询计数窗口增加 44 |
| API 缓存 hit | 9.77 ms | 与 miss 内容一致；Redis hit 计数增长；查询计数窗口增加 24 |
| 独立 CacheService Redis 不可用 | 345.49 ms | 从真实 MySQL 回源 6/6 条；错误指标为 3；未停止共享 Redis |
| 预约锁 Redis 不可用 | 见并发表 | 一次 201、一次 409，MySQL 仅一条占用；认证则按策略 fail-closed |

Hit 样本中位数比 miss 低约 68.7%。MySQL 查询计数是全局状态窗口，包含认证和采样查询，
不能视为缓存路径的精确 SQL 数。详细数据见
[cache-comparison.json](results/cache-comparison.json)。

### SSE 多连接推送

实测链路为 MySQL Outbox → Redis Pub/Sub 唤醒 → MySQL 游标 → SSE；每用户最多 5 个标签页，
每档重复 3 次。每个连接都收到面向本用户的通知，序号严格递增且无重复、丢失。

| 并发连接 | 用户数 × 标签页 | 每档期望/收到 | 推送延迟中位数 | P95 | 最大值 |
|---:|---:|---:|---:|---:|---:|
| 10 | 2 × 5 | 10/10 | 122.20 ms | 581.02 ms | 581.53 ms |
| 50 | 10 × 5 | 50/50 | 487.74 ms | 969.21 ms | 1,032.90 ms |
| 100 | 20 × 5 | 100/100 | 846.61 ms | 1,637.79 ms | 1,854.19 ms |

100 连接档全部送达，但 P95 已约 1.64 秒，说明连接数增加时推送尾延迟上升；此数据是
本机三轮小规模测量，不代表生产集群容量。见
[sse-fanout.json](results/sse-fanout.json)。

## 失败分析与修复闭环

| 发现 | 原因与修复 | 回归结果 |
|---|---|---|
| 新预约路径在并发时可能因交接记录尚不存在而发生 InnoDB gap-lock 死锁 | 对刚插入的预约跳过“缺失交接记录”的 `SELECT … FOR UPDATE`；该记录确定不存在，直接插入交接行，避免多个事务锁住同一缺失键区间。实现位置：[reservations.py](../backend/app/application/reservations.py#L244) | 后续 50/100 请求竞争、部分重叠和生命周期 API 套件通过；只保留一个同日预约赢家 |
| 维护设备用例首次断言了错误的错误码 | 实际 API 合同是 409 `RESERVATION_CONFLICT`，details 说明设备处于 MAINTENANCE；修正测试期望，没有更改产品行为 | maintenance 用例及最终 16 项套件通过 |
| 分页造数首轮触发日期唯一约束 | 1k/10k/100k 数据 cohort 的起始日期重合；将各 cohort 日期范围错开后重新完整测量 | 三档各三次采样完成 |
| Outbox 重测复用了幂等键，且把用户已有通知序号假设为 1 | 每次执行改用唯一任务键，并相对于该用户现有序号校验递增 | 双 worker 只领取一次；重复 handler 仅生成一条通知，最终套件通过 |
